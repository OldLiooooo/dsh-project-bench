# 工作台记忆：分层分片调研（研究结论，非设计提案）

> 2026-11-11 · 研究阶段。
> 背景：初版记忆机制（SQLite 账本 + 四层/七类 + claim/verified + 注入预算 + 使用期六个时刻）被判定**过于复杂**，
> 已从主提案删除并归档到 [docs/archive/memory-design-v1/](../archive/memory-design-v1/)。
> 新方向：**分片、分职责、分模块，记忆互不干扰**；本文只做调研与方案对比，不写最终设计。
>

## 0. 一页纸结论

**问题不是「记忆存得不够」，而是三件事同时错了：**

1. **粒度错了**：记忆按「项目/全局」存，执行却按「工作项/模块/角色」发生——每个会话都要加载全局记忆（阅读成本随项目线性增长），又只对其中一小片负责。
2. **装载错了**：没有「这个 agent 该读哪些片」的边界，默认「读全库再开工」；文档越写越多，注意力被稀释，任务本身的进展被固定开销吃掉。
3. **写权错了**：多个 agent/会话写同一个全局入口（当前交接、共享文档），没有单写者；表现为只追加、覆盖、死锁、重复收尾。lumio 的 `project-context.md` 是最干净的反例：名义 44 行，实际 15 KB、11 条并行「当前交接」，而收尾对账仍然 PASS。

**方向：分层 + 分片 + 装载。**

- **片 = 可写对象**（工作项 / 模块 / 角色），不是 agent、不是 session、不是时间。
- **层 = 注入预算**：顶层（全局卡 + 角色卡 + 当前工作项）≤ 2 页；模块/知识不注入，用工具按需查。
- **装载 = 角色 loadout**：每个 agent 启动只装「全局卡 + 角色卡 + 当前工作项片」，跨片只读或提回执；禁止「读全库再开工」。
- **写 = 一片一 owner**：只有 owner 写本片；跨片写入走提案/回执。
- **会话 = 临时执行上下文**：一个工作项一个活动会话；新会话必须绑定工作项并读 handoff。

**三条硬判断**（来自三个参考的交集）：

1. 顶层必须小：Anthropic 的 Claude Code 只注入 `MEMORY.md` 前 200 行 / 25 KB；更长指令会降低遵循度。
2. 单写者分片有效：Anthropic 合同 wiki 从「多 agent 写同一共享表 41/57 条」改成「一合同一页、一 agent 写」后 **57/57**；TencentDB 用 Owner/版本/ACL/loadout 把这一点工程化。
3. 可推导的信息不要进记忆：状态、进度、文件位置、计数都应「查」，不该「记」；记忆只存「不写就消失、未来会用到」的判断与经验。

**最小可行（研究级建议）**：文件分片 + 会话绑定 + 收工校验三件事先跑通；不建 SQLite 记忆库、不做向量检索、不做自动蒸馏、不上云。

## 1. 诊断：lumio 为什么越做越重（证据）

### 1.1 设计对在哪（保留）

| # | 设计 | 为什么对 |
|---|---|---|
| 1 | 四层记忆（全局规则/项目决策/模块记忆/工作项） | 分层本身就是分片；模块 README 是「唯一当前交接入口」 |
| 2 | 六字段交接 + 六字段回执 + 四档结论 | 强制带证据与回滚，杜绝「已完成」歧义 |
| 3 | 单写者 + 唯一 owner + 精确范围 | 并发写的唯一正确原语 |
| 4 | 收尾对账机检（EV_MISSING / MEMORY_BEHIND / COUNT_STALE） | 查「记录之间的一致性」，格式检查看不见「记录撒谎」 |
| 5 | 三层生效判定 + 负向探针 | 唯一能证明「规则真的会拦」的方法 |
| 6 | 计数不手抄 | 手写数字是链接检查唯一看不见的漂移 |

### 1.2 执行错在哪（数字）

| 现象 | 数字 | 后果 |
|---|---|---|
| 文档量失控 | docs **268 份 / 34,631 行**；业务代码 **3,962 行**（**8.7:1**）；docs 占插入行 **82.8%**；92/111 提交改 docs | 读文档挤占改代码的预算 |
| 人工索引退化 | file-index **399 行 / 222 条表格行 / 29 个按工作项追加的小节** | 索引变成第二份变更日志；没人靠它定位 |
| 全局交接滚雪球 | project-context 名义 44 行，实际 **15,171 字符 / 11 条并行「当前交接」**；`gate --closeout` 仍 **PASS** | 「格式通过 ≠ 内容属实」的活证据 |
| 多会话抢写 | 主工作区同时有 **92 / 188 个**别的会话未提交文件；「一个会话只管一个工作项」靠人自觉 | 冲突、覆盖、死锁 |
| 流程自身成负担 | 3,440 行工具 + 2,594 行测试治理 3,962 行代码；9 个 PR 覆盖 6 个工作项；同一 WI 同一分支三次收尾；远端残留 7 条 codex/* 分支 | 治理工具与新文档成为最大变更源 |
| 多工具各写各段 | project-context 出现「仪表盘线 / AI 收尾线 / CI 基线线」等按会话命名的并列章节，注明「本行仅追加」 | 每个 agent 只维护自己那块，没有片 owner |

### 1.3 因果链（一句话）

**全局共享记忆 + 无装载边界 + 无单写者 + 会话随意开 → 每个会话都要读全量文档 → 阅读成本超过任务进展 → 越做越难、越推越慢；而为了「不丢信息」继续加文档，正反馈自我强化。**

## 2. 两个参考怎么解决同一问题

### 2.1 Anthropic：小顶层 + 对象分片 + 单写者 + 后台巩固

| 机制 | 做法 | 对我们的含义 |
|---|---|---|
| 记忆定义 | 跨会话、可读回的经验；排除 weights/ICL/compaction | 不要把聊天原文/状态快照当记忆 |
| 写入判据 | 记忆是「对未来的预测」：只写不写就消失、未来会再用的判断/规则/计划/坑 | 状态、进度、文件位置一律查，不记 |
| 顶层小 | `global.md` = 目标/计划/记忆使用规则；Claude Code 只注入 `MEMORY.md` 前 200 行/25KB | 全局卡 ≤1 页，是硬预算 |
| 分片 | 按「问题对象」分片（locations / gameplay），按需读 | 按工作项/模块分片，不是按 agent 分片 |
| 单写者 | 一合同一页、一 agent 写、逐字引用：41/57 → 57/57 | 跨 agent 共享同一片 = 灾难 |
| 后台巩固 | dreaming 纠错/建 wiki/提升/下沉/补缺；按易变性与访问频率调 cadence | 整理要独立于主任务，初期可人工 |

### 2.2 TencentDB Agent Memory：资产化 + 装载 + 分层召回

| 机制 | 做法 | 对我们的含义 |
|---|---|---|
| 记忆资产化 | Chat Memory / Skill / Wiki / CodeGraph 统一登记 Owner/版本/可见性/状态/用量 | 「记忆」应是可治理对象，不是散文件 |
| L0–L3 分层 | L2/L3 每轮注入（≤3 条）；L1 工具按需（≤5 条）；L0 只写不读 | 预加载少量、明细工具查，保护上下文与缓存 |
| 分片键 | space × team/agent/user/task × 资产类型 × 可见性 | 片要有 owner/scope/visibility 才叫片 |
| Agent Loadout | 不同角色装配不同资产；默认模板 + 会话绑定 team/agent/task | 每个 agent 只装自己需要的；会话启动即声明作用域 |
| 默认私有 | private / team / restricted(ACL) / agent / task | 默认不共享；共享是显式动作 |
| 接入方式 | Proxy 改 base URL；DSH v0.2+ 已验证 Anthropic 路径 | 说明「统一记忆网关」可行，但我们先不上 |

### 2.3 三个交集（也是本方案的地基）

1. **小顶层 + 按需下层**：注入的是索引/当前任务，不是全量记忆。
2. **片 = 可写对象，一写者**：并发安全来自分片，而不是来自更复杂的锁/协议。
3. **按角色装载**：减少噪音、隔离职责；不同 agent 看到的记忆集合本来就不同。

## 3. 我们的约束（决定方案不能照搬）

| 约束 | 影响 |
|---|---|
| 单工作区、本地优先、git 可审计 | 记忆应首先是仓库内文件；外部记忆服务只能是可选项 |
| 人是唯一拍板者，不想维护记忆 | 分片必须自动生成/校验，不能靠人手工填表 |
| 多个 agent 工具可能并存（qoder/codex/workbuddy/dsh） | 协议必须工具无关：目录 + front matter + 少量命令；不能绑定某个宿主的内部存储 |
| DSH 是主宿主 | 注入走 `systemPrompt.section/context`；写前拦截走 `tools/pre-execute`；会话/团队/任务板可用；但**没有压缩前钩子**、默认无会话全文检索、storageDomain 无跨记录事务（见 DSH 事实文档） |
| 当前阶段是研究/单项目 | 不需要多租户 ACL、云托管、向量库；先把「一项目多 agent/多会话」治理好 |

## 4. 分层分片方案（调研级候选）

### 4.1 分片单位与目录（草案）

```text
project/
  NOW.md                  # L0 全局卡（≤1 页）：项目/阶段/周期/全局规则/索引
  roles/
    pm.md  dev.md  qa.md  # L1 角色卡（≤1 页）：读哪些片、写哪些片、禁止什么
  rules/
    global.md             # 跨片稳定规则（≤1 页）
    decisions/<module>.md # 每模块一份 append-only 决策记录（只留当前有效）
  work/
    <WI-id>/              # L2 工作项片（owner 独占，可整体归档/删除）
      task.md             # 范围/验收/计划（≤1 页）
      handoff.md          # 当前交接（≤1 页，六字段）
      evidence/           # 证据链接或小文件
  modules/
    <module>/README.md    # L2 模块片（≤1 页）：职责/接口/约束/owner/验证命令
  knowledge/
    index.md              # L3 知识索引（不注入；工具按需查）
  sessions/
    <session-id>.md       # 会话摘要（≤1 页，结束即冻结，不注入）
```

> 目录名可改，重点是**每个目录 = 一个片 = 一个 owner = 一个生命周期**；不做全局「当前交接」文件。

### 4.2 分层与装载（loadout）

| 层 | 内容 | 何时进上下文 | 预算 |
|---|---|---|---|
| L0 全局卡 | 项目名片、阶段/周期、全局规则、片索引 | 每个会话启动注入 | ≤1 页 / ≈1k tokens |
| L1 角色卡 | 该角色的读写边界、开工/收工清单 | 按角色注入 | ≤1 页 / ≈500 tokens |
| L2 当前片 | 当前工作项 task + handoff + 模块 README | 会话绑定工作项时注入 | ≤1 页 / ≈800 tokens |
| L3 知识 | 模块/文档索引、代码搜索、历史 | **不注入**，工具按需 | 单次 ≤2k |

- 总装载上限建议 **≤2 页 / ≈2k tokens**（不含用户输入）。
- 原则：**注入的必须是最新、最重要、当前任务需要的；其余都能「查」到。**
- 每片自己带「何时该读我」的入口条件（角色卡里写），避免 agent 靠猜。

### 4.3 装载流程（会话启动）

1. 会话声明：`role` + `work item`（+ 模块）；
2. 工作台生成装载包：L0 全局卡 + L1 角色卡 + L2 当前片；
3. 注入方式：DSH 用 `systemPrompt.section`（每步稳定、不进历史）或 `systemPrompt.context`（变化才追加）；其他工具用「开工先读 3 个文件」的等价命令；
4. 会话内需要跨片信息时：调索引/搜索，按需读单页；读到什么记在会话摘要里（不写回别人片）。

### 4.4 写权与并发（防干扰的核心）

| 规则 | 说明 |
|---|---|
| 一片一 owner | 工作项 owner、模块 owner、PM（全局规则）；owner 是唯一写者 |
| 跨片写 = 回执/提案 | 其他 agent 只读，需要改时写 proposal 到片 owner 的 inbox（或任务板），由 owner 落盘 |
| 会话不能写片外 | 收工校验「片外零改动」，违反即失败（工具级，不靠自觉） |
| 状态/计数/索引由生成器产出 | 人/agent 不手写；文档里只引用生成结果 |
| 决策 append-only | 每模块一份 decisions，只留当前有效，历史交给 git |
| 片可关闭 | 工作项完成后压缩为 1 页回执并归档；模块片随模块生命周期 |

### 4.5 会话纪律（治「随手开会话」）

| 规则 | 说明 |
|---|---|
| 一个工作项一个活动会话 | 默认；并行需要显式登记（worktree/写作用域） |
| 新会话必须绑定工作项 + 读 handoff | 没绑定不允许开工 |
| 结束必须写回片 | 不写 handoff 不允许收工/开新会话接手 |
| 会话数指标 | 活动会话数 ≤ 并行工作项数；超出即告警 |
| PM 会话派单 | 执行会话由 PM/人按工作项创建，不鼓励「临时聊一下」式会话 |

### 4.6 整理与提升（先手动，后自动）

| 时点 | 动作 | 产物 |
|---|---|---|
| 工作项完成 | 片压缩为 1 页回执，归档 | sessions/ + 提交 sha |
| 每周/每周期 | 合并重复、下沉细节、更新全局卡（≤1 页）、淘汰过期 | NOW.md / 模块 README / decisions |
| 可复用经验出现 | 提升为模块片约束或 Skill（版本化） | rules/ 或 skill 文件 |
| 可选（后期） | dreaming 式后台巩固：纠错、补链、提升/下沉 | 仍由 owner 审后落盘 |

> 初期不做全自动蒸馏：Anthropic 也承认 dreaming 有算力成本、产出延迟、错误/漂移风险；先人工策展。

### 4.7 写什么 / 不写什么（白名单）

| 写 | 不写 |
|---|---|
| 决策与理由、约束、踩过的坑、跨会话计划、不可推导的规则 | 进度/状态/计数、文件路径、CI 结果、聊天全文、日志、密钥 |
| 每条带来源、owner、时间、有效期 | 从代码/git/任务板能查到的任何东西 |

### 4.8 工具无关协议（多 agent 现实）

- **目录 + front matter**：`owner / status / updated_at / source / slice`；任何工具都能读写。
- **每工具开工三步**：读 `NOW.md` → 读角色卡 → 读当前片。
- **每工具收工三步**：更新当前片 handoff → 生成/更新索引 → 校验片外零改动。
- **DSH 插件只做自动化**：生成 L0/索引/装载包、拦截片外写、校验收工、可视化片健康；不把记忆放进宿主私有存储。

### 4.9 最小可行（建议先试点的 3 件事）

1. **生成全局卡 + 角色卡**（≤1 页/张），替换「全局交接 + 人工索引」；
2. **工作项片 + handoff 模板 + 会话绑定**（一个工作项一个目录、一个活动会话）；
3. **收工校验**：片外零改动、handoff 必填、索引与片一致；失败即拒绝收工。

不做：SQLite 记忆库、向量检索、自动蒸馏、复杂 ACL、云服务、dreaming。

## 5. 与初版记忆方案的差异

| 维度 | 初版（已归档） | 分层分片 |
|---|---|---|
| 记忆单元 | 项目级 SQLite 大库 + 四层/七类 | 可写对象片（工作项/模块/角色） |
| 读取 | 全局召回 + 自动注入简报 | 装载包（L0+L1+当前片）+ 按需查 |
| 写入 | agent 提案 → 服务仲裁 → claim/verified | 一片一 owner，跨片回执 |
| 多 agent | 共享一个账本，靠 scope/ACL | 各装各的片，天然隔离；共享只读 |
| 会话 | 任意开，启动注入 brief | 绑定工作项；新会话要交接 |
| 文档 | 大量全局文档 | 每片一页；知识按需 |
| 复杂度 | 高（schema/协议/状态机/评测） | 低（文件 + 规则 + 校验） |
| 失败模式 | 阅读稀释、并发覆盖、文档表演 | 分片边界/提升时机/协议遵守 |

## 6. 参考方案对比（要不要上外部记忆服务）

| 方案 | 复杂度 | 成本 | 可移植 | 适合我们吗 |
|---|---|---|---|---|
| A 文件分片 + DSH 自动化（本文推荐） | 低 | 低 | 强（git/任意工具） | ✅ 先做这个 |
| B 文件分片 + 轻索引（FTS/代码索引，可重建） | 中 | 低 | 中 | 可选，用于「查得到」 |
| C 接入 TencentDB Agent Memory 全栈 | 高 | 中（云按量） | 中（HTTP Proxy） | ❌ 现阶段过重；多团队/多项目时再评估 |
| D 自研 SQLite 记忆库（初版） | 高 | 低 | 弱 | ❌ 已判定过复杂 |

> TencentDB 值得抄的是**机制**（资产表/loadout/分层召回/会话绑定），不是**部署**；需要时可以通过 Proxy 作为可选后端，而不改工作台协议。

## 7. 风险与反模式

| 风险 | 表现 | 缓解 |
|---|---|---|
| 片太多/太碎 | 找不到、跨片跳转多 | 片数 = 工作项 + 模块；全局卡只做索引 |
| 片太大 | 又变成大文档 | 每片 ≤1 页硬上限，超出下沉到知识层 |
| 全局卡膨胀 | 又出现「15 KB 当前交接」 | 硬预算 + 生成器裁剪 + 每周审查 |
| 跨片信息靠记忆 | 漏/冲突 | 状态类信息一律查，不进记忆 |
| 会话纪律靠人自觉 | 又回到随意开 | 工具校验：绑定/片外零改动/收工必填 |
| 多工具不遵守协议 | 各写各的 | 协议极简 + 校验工具；先限定支持的工具数量 |
| 过度自动化 | 噪声/成本/幻觉 | 先人工策展；自动只做生成与校验 |
| 没有删除/归档规则 | 只增不减 | 片完成即压缩归档；全局卡定期淘汰 |

**反模式清单**：全局唯一「当前交接」；手写索引/计数/状态；多 agent 写同一页；自动注入全量记忆；把进度写进记忆；新会话「先读全库」；为了治理再写一套治理文档。

## 8. 需要拍板的问题（研究阶段）

| # | 问题 | 推荐 |
|---|---|---|
| Q1 | 分片粒度：工作项 + 模块够吗？还需要「角色片」吗？ | 工作项 + 模块为片；角色卡只是装载说明，不算片 |
| Q2 | 存储：仓库内 Markdown + front matter？DSH storageDomain 只放运行态？ | 是；记忆宿主 = 仓库文件，运行态另存 |
| Q3 | 多工具支持是不是硬需求？哪些工具必须支持？ | 若必须，协议极简 + 校验工具；否则先只支持 DSH |
| Q4 | 会话纪律：强制「一个工作项一个活动会话」？谁创建新会话？ | 是；PM/人按工作项创建 |
| Q5 | 顶层预算：L0+L1+L2 ≤2 页 / ≈2k tokens 可接受吗？ | 是；超限即下沉 |
| Q6 | 知识层：第一阶段只做文档/代码搜索，不做 Wiki/CodeGraph？ | 是；先搜索，知识图后置 |
| Q7 | 整理：周会人工策展，还是引入自动 dreaming？ | 先人工；自动后置 |
| Q8 | 是否引入 TencentDB/云记忆作为可选后端？ | 现阶段不引入；保留 Proxy 可能性 |
| Q9 | lumio 哪些机制保留？ | 四层/六字段/单写者/收尾对账保留；file-index、全局交接、手工编号删除 |
| Q10 | 片外写校验：worktree 硬隔离还是收工检查？ | 两者都要：写时最小隔离 + 收工硬校验 |
