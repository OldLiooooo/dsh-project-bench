## 0. 结论

一句话：**lumio 的结构设计比我们的初版清醒得多（分层记忆、单写者、机器收尾对账、四档结论），但它把「记录完整」当成「执行正确」——每条正确规则都靠人手写文档兑现，最终文档量把规则本身稀释掉了。**

| 判定 | 内容 | 依据 |
|---|---|---|
| 设计对 6 条 | 四层记忆、六字段交接/回执、单写者+精确范围、closeout 记录对账、三层生效判定、不手抄数字 | §1.5 |
| 执行错 3 类 | 体量失控（文档:代码 = 8.7:1）、交接只增不减（11 条并行「当前交接」）、流程自身重复（同一 WI 开 3 个 PR） | §2 |
| 被稀释 8 处 | 长文档、人工索引、多份状态、开工前置阅读、交接不可关闭、收尾仪式、文档即交付、手工编号治理 | §3 |
| 重做 | 保留 5、删除 5、压到一页 3 | §4 |

### 1.2 交接与回执

- 六字段交接：身份 / 已完成 / 下一步（≤3）/ 卡点 / 验证 / 回滚（`memory-and-handoff.md:20-28`）。
- 六字段跨 agent 回执：结论 / 已改文件 / 验证证据 / 剩余差距 / 下一步 / 回滚点（`multi-agent-collaboration.md:19-26`）。
- 四档结论口径：设计完成 / 实现完成 / 验收完成 / 部分完成 / 阻塞，且「没有运行证据不把实现记为验收」（`:15-17`）。
- 权威顺序里专门有一条：「代码存在不等于功能已验收；单元测试通过不等于真实环境可用；文档描述不替代运行证据」（`AGENTS.md:15`）。

### 1.3 检查：三层判定 + 收尾对账

| 机制 | 位置 | 抓什么 |
|---|---|---|
| 三层生效判定（写下来 / 可机检 / 真实路径必然执行 + 负向探针） | `evidence-and-verification.md:18-30` | 规则是否只是纸面 |
| `gate --closeout`：EV_MISSING / MEMORY_BEHIND / COUNT_STALE / WI_STATUS_STALE / RECOVERY_PATH_MISSING | `multi-agent-collaboration.md:50-58`；实现 `tools/engineering/closeout.mjs:33-100` | 记录之间的一致性 |
| `verify` 档位 fast/gate/code/full，pre-push 自动 code | `AGENTS.md:35` | 单一验证入口 |
| 计数不手抄，粘贴 `--json` 原文 | `evidence-and-verification.md:54-58` | 硬编码数字漂移 |
| 编号 + claims 独占锁 | `coordinate.mjs`；`multi-agent-collaboration.md:30-34` | 同工作区并发写 |

### 1.4 多 agent 协作

责任模型：一个工作项一个可区分 owner，同一文件同一时间只有一个写者；子 agent 只能在父项已登记范围内分工，由负责人登记每个文件的唯一写者；他人维护的记忆只能「经回执请求更新，不能直接覆盖」（`multi-agent-collaboration.md:7-11`、`memory-and-handoff.md:37`）。收尾必须「收齐回执 → 核对范围/交叉引用/证据 → 更新工作项与入口 → 释放认领」（`:48`）。

### 1.5 哪些设计真正是对的

| # | 设计 | 为什么对 | 反证（没有它会怎样） |
|---|---|---|---|
| 1 | 单一交付入口 `--pr` + 禁止手 commit/push | 唯一路径才能谈一致 | 曾并存两代收尾工具，产生 8 次重复收尾、多条平行分支（`DEC-20261109-001:15`） |
| 2 | 收尾对账机检「记录之间的一致性」 | 格式检查看不见「记录撒谎」 | `closeout.mjs:48-59` 注释直接点明 MEMORY_BEHIND 的后果：新会话从假前提开始，比没有记忆更糟 |
| 3 | 六字段交接 / 回执 + 四档结论口径 | 强制带证据与回滚，杜绝「已完成」歧义 | 17/48 工作项写着「实现完成（未验收）」，至少口径没被抹平 |
| 4 | 单写者 + 唯一 owner + 精确范围 | 并发写的唯一正确原语 | 主工作区曾同时有 92 / 188 个别的会话未提交文件（`EV-20261109-003:155`、`EV-20261109-005:75`） |
| 5 | 三层生效判定 + 负向探针 | 唯一能证明「规则真的会拦」的方法 | 钩子权限 100644 导致全新克隆静默跳过，就是纸面规则 |
| 6 | 不手抄数字（COUNT_STALE） | 硬编码计数是链接检查唯一看不见的漂移 | 作者自己记录过「58 模块/186 文件 vs 索引 60/207」（`evidence-and-verification.md:56`） |

### 2.2 file-index：不是索引，是第二份变更日志

`docs/memory/file-index.md`：399 行 / 63 KB / **222 条表格行** / **29 个按工作项追加的小节**（`:57` 起每个 WI 一节，排到 `:391`）。规则要求「每个本规则生效后新建的文件都应有一条记录」（`:17`），且「文件头」也要写同组信息（`:19`）——同一事实写两遍，由 agent 手工维护。它的增长方式与工作项一一对应，索引因此退化成「谁在什么时候加了哪些文件」的流水账；而「这个模块现在归谁、该读哪」仍需另查 `module-index.md`（27 行）与各模块 README。

### 2.3 交接链堆叠：一个「当前交接」里躺着 11 份当前交接

`docs/memory/project-context.md` 名义 44 行，实际 **15,171 字符**：

| 现象 | 数字 | 位置 |
|---|---|---|
| 并行的交接条目 | **11 条**（5–20 行），其中 2 条「最新交接」、3 条「上一交接」 | `:5-9` |
| 独立成段的六字段交接 | 1 组（身份/已完成/下一步/卡点/验证/回滚） | `:10-15` |
| 明确声明「只追加不改写」 | 2 条 | `:16`、`:20`（「本行仅追加仪表盘线交接，不改写上方产品设计线内容」） |
| 单条最长 | **1,078 字符**（一行讲完一个工作项的全部细节） | `:5` |
| 机检结果 | 审计时实跑 `node tools/engineering/gate.mjs --closeout` → **PASS** | 附录 A |

这正是作者自己写下的风险：规范要求「当前交接只更新当前事实，历史过程保存在工作项」（`memory-and-handoff.md:30`），但删除历史在实践中被视为不可接受，于是「当前」变成「全部」，记忆入口从 1 页变成 15 KB 的滚雪球——**所有机检都通过**。

## 3. 哪些机制反而稀释了注意力

| # | 机制 | 怎么稀释 | 量级 |
|---|---|---|---|
| 1 | 长文档 | 读完才能判断，读完就没预算改 | 文档 34,631 行 vs 代码 3,962 行；单条交接 1,078 字符 |
| 2 | 人工索引 | 改一个文件要写索引 + 文件头两处；索引本身要读 399 行 | file-index 222 行 / 63 KB，29 个追加小节 |
| 3 | 多份状态 | 同一「当前状态」存在于 project-context、module-index、file-index、specs/index.json、WI、EV、dashboard、各 README | 至少 8 处，互不自动同步（只有 COUNT_STALE 的 2 个正则兜底） |
| 4 | 开工前置阅读 | AGENTS 62 + engineering 537 + memory 71 = 670 行起步；实际定位还要读 project-context（15 KB）+ 相关 DEC（39 份里挑）+ WI 模板 | 约 1,000+ 行 / 60 KB+ 才开始写第一行 |
| 5 | 交接不可关闭 | MEMORY_BEHIND 要求「最新已完成的 WI 必须出现在 project-context」，于是每个会话都必须写同一个全局文件；又因为「历史不删」，文件只增不减 | 44 次提交改同一文件，堆积 11 条并行交接 |
| 6 | 收尾仪式 | 一次工具改动 = AGENTS + DEC + EV + WI + file-index + project-context + tools README + 规则文档 | 样例提交 `d479ecd` 共 20 文件，其中 **8 个是文档/规则** |
| 7 | 文档即交付 | 48 WI / 39 DEC / 31 EV / 261 条冻结 AC 全部「未执行」；结论被迫写成「实现完成（未验收）」 | 261 条 AC 散布 48 份产品文档，0 条执行 |
| 8 | 手工治理编号与 owner | 需要负责人预留编号区间、人工判重、人工清理分支 | 撞号 1 次；残留 7 条分支；owner 规则改两轮才去厂商化 |

注意：这些机制**单看每一条都合理**，问题是互相叠加——写（索引）+ 写（交接）+ 写（证据）+ 写（决策）+ 写（模块 README）是五份必须同步的人工副本。agent 的注意力预算被五份副本分摊后，真正读代码的预算接近零。这就是「任务越做越难、进度推不动」的机制来源。

## 4. 如果重来：保留 / 删除 / 压到一页

### 4.1 保留（5）

| 保留 | 理由 | 落地要求（比 lumio 更硬） |
|---|---|---|
| 单一交付入口 + 失败关闭 | 唯一路径是对抗「平行分支/重复收尾」的唯一手段 | 入口只允许 1 个，文档只允许 1 处描述；其余只能链接 |
| 收尾对账机检 | 记录一致性是 LLM 最容易骗过下一个会话的地方 | 检查码 ≤5 个；每个码必须有负向探针 |
| 六字段回执 + 四档结论 | 强制带证据与回滚，杜绝「已完成」歧义 | 字段固定，每字段 ≤3 行 |
| 单写者 + 唯一 owner + 精确范围 | 并发写的正确原语 | owner 由运行时任务板持有，不写进散文 |
| 三层生效判定 + 不手抄数字 | 唯一能区分「纸面规则」和「真拦得住」的方法 | 计数由生成器产出，人不写数字 |

### 4.2 删除（5）

| 删除 | 替代 |
|---|---|
| 逐文件人工 file-index（399 行） | 由脚本从目录树/依赖生成只读清单；或直接删，需要时 glob |
| 全局手写「当前交接」累积链（15 KB / 11 条） | 每片一个 WI 文件 + 机器生成的一页 NOW（当前片、下一步 3 条、卡点、验证命令、回滚点） |
| 39 份 DEC 的无边界增长 | 每模块 1 个 `decisions.md` 只留「当前有效」，历史交给 git |
| 4 处重复的交付链说明（`AGENTS.md:51-61`、`development-rules.md:87`、`tools/engineering/README.md`、`.workflow/README.md` 全 157 行） | 1 份规范 + 其余链接 |
| 自动 WI 编号协调器 + 手工编号预留区间（`coordinate.mjs` 286 行） | 任务板 ID 由工具分配，文档只引用 ID |

### 4.3 压到一页（3）

| 文档 | 现在 | 目标 |
|---|---|---|
| 全局入口 `AGENTS.md` | 62 行，仍可接受，但夹带 11 行交付链细节 | ≤40 行：权威顺序 5 行、禁止事项 5 行、「去哪找」一张表、收尾 3 条命令 |
| 模块入口（模块 README） | 目标 84 个目录 README，实际 109 份 | 只保留「有人改的模块」，每份 ≤1 页：职责 / 合同 / 当前片 / 验证命令 |
| 交接（每片一份） | 15 KB 全局 + 44 次提交 | 每片 ≤1 页，字段固定，写完即冻结；新片新文件，不追加旧文件 |

### 4.4 对「分片 / 分职责 / 分模块」的具体启示

| 原则 | lumio 的对应失败 | 具体做法 |
|---|---|---|
| **一个模块一个入口** | 模块状态同时写在 module-index、file-index、project-context、WI、EV 五处 | 每模块只有 1 份 `README.md`（≤1 页），其他文档只能链接，禁止复述状态 |
| **一个工作项一个片** | WI、EV、patch、doc 改动分散 5 个目录，靠 file-index 缝合 | 片 = 一个目录 `work/<id>/`（WI.md + EV/ + patch/ + 回执），可整体归档/删除，片内自洽 |
| **agent 只读自己片** | 无装载边界，开工要读 AGENTS + engineering + memory + DEC | 装载清单 = 全局规则（≤1 页）+ 本片目录；跨片信息只通过回执摘要获取，禁止「读全库再开工」 |
| **跨片只走回执** | 共享 `project-context.md` 被多会话争写，产生 MEMORY_BEHIND 死锁 | 片 owner 独占本片写权；跨片写 = 发回执给 owner，由 owner 落盘；工具拒绝越片写 |
| **状态只在一处** | 8 处状态副本，靠 2 个正则兜底 | 状态由任务板/生成器产出；文档里的状态是渲染结果，不可手改（改了下次生成被覆盖） |
| **计数不写进散文** | 207 vs 215 漂移；COUNT_STALE 只覆盖两种写法 | 任何数字都由脚本生成，禁止手写；检查器只查「是否与生成器一致」 |
| **会话隔离由工具保证** | 「靠人自觉」；92/188 个他人脏文件 | 每片一个 worktree/工作目录，工具在收尾时校验「片外零改动」，否则失败关闭 |
| **片要能删** | 历史不可删 → project-context 只增不减 | 片完成后整体压缩为 1 页回执；原文进 git 历史，工作区删除（保留 sha） |

## 5. 不要重犯的硬教训（5 条）

1. **文档量超过代码量时，文档不再是资产而是负担。** lumio 用 34,631 行文档治理 3,962 行代码（8.7:1，插入行占 82.8%），首批 48 个工作项里 17 个「实现完成未验收」。判断标准只能是：这份文档下一次决策会被读吗？不会就删。
2. **任何手写的索引、计数、状态都必然漂移；只有「生成」或「机检」二选一。** lumio 抽了 COUNT_STALE，却仍漏掉 `docs/README.md:30` 的 207（实为 215）——因为检查器只匹配两种写法。手工索引不是被维护坏的，是设计上注定坏。
3. **「一个全局当前交接文件」是并发毒药。** 它强迫每个会话写同一文件，直接产出 MEMORY_BEHIND 死锁（worktree FAIL / 主检出 PASS）和 11 条并行「最新交接」。记忆必须可分区、可合并、可关闭；不能有唯一的「当前」。
4. **流程自己会成为主要工作量。** 3,440 行工具 + 2,594 行测试治理 3,962 行代码；同一个工作项开 3 个 PR（!4/!5/!6）、8 次重复收尾。当一个流程的产物需要 8 份文档同步，它已经在和主任务竞争同一个注意力预算。
5. **「格式通过不等于内容属实」要当成第一原则，而不是免责声明。** lumio 自己写下了这句话（`memory-and-handoff.md:43`），但 `gate --closeout` 在 15 KB 滚雪球的交接上依然 PASS。检查必须绑在可执行证据（命令 + 退出码 + 负向探针）上；凡是用「文档写得好」证明「做得好」的机制，最终都会变成文档表演。
