# 周期复盘

复盘不是「总结一下这周」，是**把这一周期的事实固定下来，供下一周期形成决策**。

## 数据从哪来（不用手填）

| 要什么 | 从哪取 |
|---|---|
| 进度 | `project_status` 的 `progress`（唯一口径 = verified） |
| 本期完成 | `verified_at` 在本期内的切片 |
| 本期验收次数 | `slice/verify` 事件（period 内） |
| 待决策 / 阻塞 | `project_status` 的 `pendingDecisions` / blocked 计数 |
| 周报 | `weekly_report({mode:'preview'})` —— **直接用它，不要自己编数字** |

## 四段式

1. **做成了什么**：本期 verified 的切片 + 验收人。只写验过的，不写「基本完成」。
2. **没做成什么、为什么**：卡在哪一类——需求不清 / 缺决策 / 被阻塞 / 估错范围。
   要能对应到具体切片 key，不要写「沟通不畅」这种不可行动的结论。
3. **口径是否可信**：本期有没有「done 未验收」堆积？有就是验收环节成了瓶颈，不是交付快。
4. **下期改什么**：最多 3 条，每条必须是**下一周期能验证的规则变更**（例如「S1 阶段禁止出 ADR」）。

## 推进周期

复盘写完，用 `period_roll({ note: '<本期一句话结论>' })` 推进。
它会：写 `period/roll` 事件、把**本期验证数定格**在事件 payload 里（推完就再也算不出历史吞吐，所以必须现在定）。

> 注意：`period_roll` 不做日历自动滚动。「这一周期做了什么」是复盘与指标的分母，
> 自动按日历滚动会把跨零点的提交归到哪个周期变成靠时钟猜的事。
